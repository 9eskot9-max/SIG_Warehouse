## Router recognition and party-hint work — coded, not deployed (9 November 2026)

The isolated topic branch `codex/bank-router-review-redesign` adds an auditable `SNB Party Hint Rule` registry and a cleaner review card. A rule is keyed by SNB, a fingerprint of the full company account, direction, statement narrative family, hint kind and normalized exact hint. The account ending is shown for human orientation. Distinct families are IPS local, internal SNB and larger-local narrative; the classifier uses parser/statement text and **does not classify by SAR 20,000 alone**. One ERP party can have many rules across company accounts, formats and individual hints. The Router refuses to point an active key at a second party; a deliberate change made in Sheet Am is a last-write-wins edit with an audit entry, while two Sheet rows giving one hint to two parties are both rejected. Revoke/reactivate actions retain an audit trail. Hint kinds are NAME, ACCOUNT, BEN_ID (outgoing) and DEP_ID (incoming internal transfers); numbers that match our own accounts are never offered as payer hints. See `ERPNext/docs/bank_router_structure_v2_handoff_20261109.md` for the current structure.

The movement card searches permission-visible, enabled ERP Customers or Suppliers that are explicitly approved in the new router approval registry. The registry starts empty: Accounts Managers or System Managers approve each exact ERP ID through the page; revoking an approval also revokes its active hint rules. Existing saved decisions are preserved. A confirmed rule produces suggestions in ERP at once; ERP is the authority and Sheet Am receives a copy on the next sync. Each movement still needs its own review decision. Rules do not allocate invoices, create accounting entries or submit documents. Known TAWAL aliases and deferred TAWAL routes are excluded; Alinma does not inherit SNB hint rules.

The local importer also reads the Am transfer-request registry and carries a category only when its maker Txn ID uniquely appears in statement narrative or the existing beneficiary + amount + Riyadh-date matcher returns one row. Ambiguous/conflicting candidates remain unassigned. `XXPC` is displayed as **Petty Cash**. Any Employee text in transfer evidence remains evidence only; this router does not assign an Employee or resolve custody ledgers.

The staged `router_revamp_sync.staged.mjs` keeps Sheet Am's tab `snb_party_hint_rules` in step with ERP in both directions. Push: pending ERP rules are written to a readable, hand-editable tab (status, account ending, format, hint, party type, ERP ID, party name first; machine columns last) and ERP acknowledges only the unchanged rule version; rejected or failed versions are marked failed and the page can queue a retry. Pull: rows typed or edited in the Sheet are sent to `import_sheet_hint_rules`, where ERP validates each one (known account ending, approved enabled party, length, not our own account, no hint given to two parties) and reports rejections per row without stopping the rest. The hub only stores, stamps and lists rows; it no longer matches statement rows or writes suggestion columns. A hub version check prevents publication before the matching Apps Script version is deployed. The existing scheduled `router_basic_sync.mjs` has been restored to its pre-revamp behavior; the staged bridge must be released deliberately with the app and hub. This handoff is **code only**: no production mapping was written.

The staged local bridge derives fee/VAT family links from Am's explicit parent key or a unique full-source-account + bank-reference pair. The default unposted/unconfirmed filter now uses live read-back for a linked PE or JE only when its marker is unique and visible, the exact document, SNB source-account fingerprint, mapped bank GL, currency and amount agree, and both accounting DocTypes and the linked accounts are readable. A main movement remains visible if any linked fee is draft or unknown. Missing, cancelled, ambiguous and inaccessible documents stay visible. A journal's marker alone does not identify the bank. The list does not create a payment or prove that a document is reconciled to a particular statement row. ## Scope and boundaries

- This implementation saves review decisions, but **does not create, reconcile, or submit JE/PE drafts**. A bank row or a supplied ERP link is only a hint, not a verified accounting document.
- SNB's current local queue builder requires a Sheet Am JSON export to load beneficiary and transfer-request evidence; Alinma's initial received-credit and salary-candidate lanes do not depend on SNB beneficiary or transfer data. Customer, invoice, payroll, and ERP account matching remain unimplemented for Alinma.
- Review the full source JSON for data scope before production ingestion. Accounts User, Accounts Manager and System Manager retain read/write/create/report on `SNB Movement Review`; the same three roles can open the existing Page. The feature adds only read access at permlevel 0 for Accounts User and Accounts Manager on Purchase Order. Its migration preserves the complete existing Custom DocPerm matrix and stops if that baseline differs. User Permissions continue to filter the Purchase Order lookup. Delete/submit/cancel on the review DocType are not granted. The intake method additionally requires the configured integration owner or System Manager. The controller forbids ordinary form/REST writes outside the router methods.
- **Acceptance status: NOT TESTED.** Fresh-session Accounts User/Accounts Manager workflows, System Manager and denied outside-role behavior, linked Supplier/Company/Purchase Order/Purchase Invoice reads, Arabic/English rendering, repeated ingestion and changed-source conflict handling remain follow-up acceptance. Deployment does not claim those workflows are verified. Any Alinma salary or received-credit accounting route remains a human decision; there is no ERP draft creation.
- Source immutability includes the entire `source` object; a changed parser output, enrichment, or family metadata may produce a source conflict. The Alinma adapter uses account + date + reference + signed amount identity, masks the account to its last four digits in ERP evidence, and does not send salary-transfer initiation data. Handle a conflict deliberately rather than replacing statement evidence.
- Own-account pairing, XXPC custody checks, supplier consistency, SADAD mappings, payment draft creation, ERP document read-back and recovery after uncertain draft creation remain outside the router. Review-page PO/PI link selection is not a Payment Entry or a reconciliation action.

An Alinma ERP push requires the same configured integration-owner credentials and explicit `--push`; do not run it until the source has been reviewed and the non-admin acceptance gate has been completed.
